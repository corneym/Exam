The current UI is too tightly coupling “shared preamble” with “multipart question”. That is why your MCQ case falls through the gap.

There are actually two different relationships:

A multipart source question, such as 21a, 21b, where both parts belong to source question 21 and may share a preamble.
Separate questions, such as MCQ 5 and MCQ 6, which remain independent questions but happen to use the same stimulus/context.

Those should not be represented the same way. In particular, I would not invent a SourceQuestion joining Q5 and Q6 just to make the existing UI work.

The underlying model is already much closer to supporting this than the UI is. A Question can have a SharedQuestionContext without having a SourceQuestion, and the capture service can persist a selected/new shared context independently of whether a source-question code was derived. The current limitation is mainly that QuestionCapturePane only offers the automatic preamble controls when SourceQuestionCodeParser recognises a multipart code.

I think the eventual UI should make “Shared context” an explicit, general part of Question capture rather than something inferred solely from the question number. Something like:

Question
  Code:          5
  Marks:         1
  Response:      (x) Multiple choice   ( ) Written response

  Shared context:
      (x) None
      ( ) Capture new
      ( ) Reuse existing

For your example, you would capture Q5 like this:

Shared context: Capture new
→ draw the shared stimulus
→ Add Context
→ draw Q5's own region
→ Save Q5

Then Q6:

Shared context: Reuse existing
→ choose the context just captured for Q5
→ draw Q6's own region
→ Save Q6

Q5 and Q6 remain ordinary independent MCQs. They simply both reference the same SharedQuestionContext.

For multipart questions such as 21a and 21b, we can retain the useful automatic behaviour. If the question code indicates a multipart source question, the application can still infer/reuse the shared context associated with source question 21. So this would extend the current design rather than replace it.

I would also consider a small convenience after saving Q5: when the next question is being entered, the Shared context section could offer something like:

Reuse previous: "Q5 shared context"

but I would make that an explicit click rather than automatically carrying it forward. Automatic carry-forward would eventually attach a context to Q7 by mistake.

One terminology change may help as well. The current checkbox says:

First region is shared preamble

That wording describes one particular capture technique, not the underlying concept. I think the UI should use Shared context as the general concept, with “Capture new shared context” and “Reuse shared context”. “Preamble” can remain appropriate when dealing specifically with multipart questions and the legacy preamble semantics.

So I would record this as a genuine Sprint 9 capture-UI gap, not something to fix by storing duplicate regions. Your two-region workaround is safe for the questions you're capturing now, but the proper design is to allow a shared context across otherwise independent questions, including MCQs.
